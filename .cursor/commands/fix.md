# イシュー対応

## 概要

`#イシュー番号` を指定し、Git Worktree を使用した独立環境で実装から PR 作成まで実行します。

## 使用例

- `/fix #123` - イシュー #123 に対応

## 手順

### 1. イシュー取得

```bash
cd /Users/takahashikotaro/src/github/k4h4shi/mechanix
gh issue view <番号>
```

### 2. ワークツリー作成

ブランチを直接チェックアウトするのではなく、Git Worktree を使用して独立した環境を作成します。

1.  `worktree-manager` スキルを使用し、以下の設定でワークツリーを作成してください:
    - Branch: `feature/issue-<番号>` (または `fix/issue-<番号>`)
    - Base: `origin/main`
    - スキルが自動的にディレクトリ作成 (`.worktrees/` 配下)、`git worktree add`、依存関係の初期化を行います。

2.  作成されたワークツリーへ移動:
    ```bash
    cd .worktrees/<branch-name>
    ```
    **これ以降の作業は全てこのディレクトリ内で行ってください。**

### 3. 実装（正規 TDD + 入れ子構造）

イシュー内容に基づき、**Kent Beck の正規 TDD** で開発する。
入れ子構造とは、TDD サイクルを E2E と単体テストで再帰的に実行する手法。

> 参考: [【翻訳】テスト駆動開発の定義](https://t-wada.hatenablog.jp/entry/canon-tdd-by-kent-beck)

#### Kent Beck による TDD の定義

```
1. テストリストを書く
2. テストリストから「ひとつだけ」選び、テストを書く（失敗を確認）
3. テストを成功させる（気づいたことはテストリストに追加）
4. 必要に応じてリファクタリングを行う
5. テストリストが空になるまでステップ 2 に戻る
```

#### 核心原則

**テストが Red でない限り、プロダクションコードを修正してはならない。**

- コードを書く前に全てのテストを書くことではない
- テストを「ひとつだけ」選び、小さく進める
- テストリストで全体像を把握しながら、一歩ずつ進む

#### ステップ 0: テストリストを書く

**実装を始める前に、テストリストを作成する。** これが TDD の起点。

イシューを分析し、検証すべきシナリオを洗い出す:

```markdown
## テストリスト

- [ ] ユーザーがログインできる
- [ ] 無効なパスワードでエラーが表示される
- [ ] 未登録ユーザーでエラーが表示される
- [ ] ログイン後にダッシュボードにリダイレクトされる
```

テストリストは:

- 開発中に気づいたことを随時追加してよい
- 優先度や依存関係を考慮して順序を決める
- 完了したらチェックを入れる

#### ステップ 1: テストを「ひとつだけ」選ぶ

テストリストから**ひとつだけ**選び、具体的で実行可能なテストコードに翻訳する。

E2E テストを優先:

```typescript
// e2e/auth.spec.ts
test("ユーザーがログインできる", async ({ page }) => {
  await page.goto("/login");
  await page.fill('[name="email"]', "test@example.com");
  await page.fill('[name="password"]', "password123");
  await page.click('button[type="submit"]');
  await expect(page).toHaveURL("/dashboard");
});
```

**テストが失敗することを確認する（Red）。**

#### ステップ 2: テストを成功させる（Green）

**最短で**テストを通す。いきなり本実装をしない。

- モックやハードコードで OK
- 完璧な設計より、まず動くこと
- 気づいたことはテストリストに追加

```typescript
// 仮実装: ハードコードで通す
export async function login(email: string, password: string) {
  return { success: true, redirectTo: "/dashboard" };
}
```

#### ステップ 3: リファクタリング + 内側 TDD

Green になったら、仮実装を本実装に置き換える。
**本実装が必要な箇所は、単体テストで再び TDD を回す（入れ子構造）。**

```
┌─────────────────────────────────────────────────────────────┐
│ 外側: E2E テストで機能全体を検証                            │
│                                                              │
│   テストリスト → Red → Green → Refactor                     │
│                            ↓                                │
│   ┌────────────────────────────────────────────────────────┐│
│   │ 内側: 単体テストで個別モジュールを検証                 ││
│   │                                                         ││
│   │   Unit Red → Unit Green → Unit Refactor                ││
│   └────────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────┘
```

単体テストを書く対象:

- 純粋関数やユーティリティ
- E2E では検証しにくいエッジケース（境界値、異常系）
- 複雑なビジネスロジック

#### ステップ 4: テスト整理

**テストも含めてリファクタリングする。**

削除・整理すべきテスト:

- E2E で既にカバーされている単体テスト
- 重複している検証
- 開発途中の冗長なテスト

残すべきテスト:

- 純粋関数のテスト（E2E では直接検証できない）
- E2E では網羅しにくいエッジケース
- 高速なフィードバックが必要なロジック

整理の手法:

- 似たケースは `it.each` 等でまとめる
- E2E 優先: 同じ動作を検証するなら E2E を残す

#### ステップ 5: 次のテストへ

テストリストから次のテストを選び、ステップ 1 に戻る。
**テストリストが空になるまで繰り返す。**

#### 実践例

```markdown
## テストリスト

- [x] ユーザーがログインできる
- [ ] 無効なパスワードでエラーが表示される ← 次はこれ
- [ ] 未登録ユーザーでエラーが表示される
```

1. **Red**: `e2e/auth.spec.ts` に「ログインできる」テストを書く → 失敗
2. **Green**: 最短で通す（ハードコード・モックで OK）
3. **Refactor**: 本実装に置き換え
   - 純粋関数 `isValidRole` → **単体テストで Red にしてから実装**
   - バリデーション `loginSchema` → **単体テストで Red にしてから実装**
4. **テスト整理**:
   - `loginSchema` の単体テストは E2E でカバー済み → **削除**
   - `isValidRole` の単体テストは E2E では検証できない → **残す**
5. **次へ**: テストリストから「無効なパスワードでエラー」を選ぶ

### 4. 確認

```bash
# ワークツリー内で実行
cd web && npm run lint && npm run build && npm test
```

### 5. コミット＆プッシュ

```bash
git add -A && git commit -m "feat: #<番号> に対応"
git push -u origin HEAD
```

### 6. PR 作成

```bash
gh pr create --title "タイトル" --body "## 概要
変更内容の説明

## 変更点
- 変更1
- 変更2

Closes #<番号>" --base main
```

### 7. CI 確認

```bash
gh pr checks <PR番号>
```

## 注意事項

- コミットメッセージは日本語
- `Closes #番号` でイシューをリンク
- CI 失敗時は修正して再プッシュ
