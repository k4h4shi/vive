# コードレビュー（静的解析）

Git Worktree を使用した独立環境で、プルリクエストの静的コードレビューを実行します。
**このコマンドの実行中に、ワークツリーの削除やコードの変更は絶対に行わないでください。**

## 使用例

- `/review #123` - PR #123 のコードをレビュー

## 手順

### 1. ワークツリーのセットアップ

1.  **PR 情報の取得**:

    ```bash
    gh pr view <PR番号> --json headRefName,baseRefName
    ```

    - `headRefName`: ソースブランチ名（例: `feature/issue-123`）
    - `baseRefName`: ターゲットブランチ名（例: `main`）

2.  **既存ワークツリーの確認**:

    - `git worktree list` を実行し、`headRefName` のワークツリーが既に存在しないか確認します。
    - **もし存在する場合**: そのワークツリーが作業用に使われている可能性があるため、新しいワークツリーは作成せず、既存のものを利用してレビューを続行します。
    - **存在しない場合**: 次のステップに進み、新しいワークツリーを作成します。

3.  **ワークツリーの作成（必要な場合のみ）**:

    - `worktree-manager` スキルを使用します。
    - **Branch**: 上記で取得した `headRefName` を指定。
    - **Base**: `baseRefName` (通常は `origin/main`)。
    - **注意**: 静的レビューのみを行うため、`npm install` や DB セットアップ等の**環境初期化ステップはスキップ可能**です（所要時間の短縮）。

4.  **コンテキスト切り替え**:
    ```bash
    cd .worktrees/<branch-name>
    ```

### 2. レビュー実施

プロジェクトのガイドライン (`.cursor/rules/`) に基づきコードを分析します。

#### 分析コマンド

```bash
# 変更ファイル一覧の取得
git diff --name-only origin/main...HEAD

# 必要に応じて各ファイルを read_file ツールで読み込み確認
```

#### レビュー観点（トレーサビリティと整合性）

要件、仕様、コード、テストの間で厳密な整合性を確認してください（@AGENTS.md）。

| レイヤー         | 対応ドキュメント (仕様)                     | 確認責任とカバレッジ                                                                         |
| :--------------- | :------------------------------------------ | :------------------------------------------------------------------------------------------- |
| **Requirements** | `usecases.md`                               | 新機能はスコープ定義に含まれているか？                                                       |
| **E2E Test**     | `usecases.md`<br>`screen-specs.md`          | `usecases.md` の全シナリオと `screen-specs.md` の UI 挙動をカバーしているか？                |
| **Integration**  | `state-transitions.md`<br>`domain-logic.md` | 複雑な状態遷移やドメインロジックの組み合わせをテストしているか？                             |
| **Unit Test**    | `domain-logic.md`<br>`state-transitions.md` | 個別のルール、計算、ガード条件をモジュール単位でテストしているか？                           |
| **Schema**       | `er.md`                                     | `schema.prisma` は `er.md` と一致しているか？（スキーマ変更時は `er.md` も更新されているか） |

**原則**: 要件と仕様は乖離してはならない。ソースコードとテストは仕様と一致しなければならない。

#### その他の観点

- **アーキテクチャ**: レイヤー分離 (`Presentation -> Service -> Domain <- Repository`) は守られているか。
- **ドメインロジック**: ドメイン層は純粋関数で実装されているか。
- **Prisma**: UI コンポーネントや Service 層から直接 Prisma を呼んでいないか（Repository 経由か）。
- **コンポーネント**: shadcn/ui の使用法、React Hook Form + Zod パターンは適切か。
- **命名・型**: 適切な命名規則、`any` を避けた厳格な型定義ができているか。

### 3. レビュー報告

GitHub PR にコメントを投稿します。シェルのエスケープ問題を避けるため、レビュー内容は一時ファイルに書き出してから `gh` コマンドに渡します。

1.  **レビュー内容をファイルに書き出す**:

    ```bash
    # `write_file` ツールを使用
    # content: レビュー内容のマークダウン
    # file_path: ./.tmp/review_body.md （プロジェクトルートに .tmp ディレクトリを作成）
    ```

2.  **PR にコメントを投稿**:

    ```bash
    gh pr review <PR番号> --comment --body-file ./.tmp/review_body.md
    ```

    **レビューコメントは日本語で記述してください。**

    **レビューコメントのテンプレート**:

    ```markdown
    ## レビューサマリ

    （全体的な印象）

    ## トレーサビリティ・整合性チェック

    - [ ] Requirements: ...
    - [ ] Docs/Specs: ...
    - [ ] Tests: ...

    ## 重要事項（要修正）

    - ...

    ## 改善提案

    - ...
    ```
